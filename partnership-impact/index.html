Executive summary

Visible experiences backed by invisible infrastructure.

Liberating Humanity received a new production website centered on Paul Hutchinson’s mission, humanitarian ecosystem, teachings, media presence, speaking, retreats, and conversion paths. Santuario received a complete 17-route redesign that restored the depth of the retreat experience, guest proof, medicine education, preparation, legal pages, boutique, and inquiry flow.

Those systems matter because a public page is only durable when the team can understand how it was produced, reproduce it, verify it, and recover it.

Report status discipline

Deployed / verified means the work is live and tied to a URL, repository state, deployment record, or proof receipt.

Completed / internal means a durable artifact or audit exists, even when it is not a public page.

Open / pending means useful work exists but the final production or account-level finish line is not yet proven.

This distinction prevents plans, assignments, mockups, or disconnected integrations from being presented as completed client value.

Cloudflare + OpenNext delivery architecture

Why Cloudflare was part of the product—not just a hosting choice.

The Liberating Humanity application uses a Next.js 16 → OpenNext for Cloudflare → Cloudflare Worker and static-assets deployment model. Next.js supplies the application and metadata framework; OpenNext adapts that application to Cloudflare’s runtime; the Worker becomes the versioned production execution layer at the edge.

GitHub source ↓ reviewed pull request Next.js application ↓ deterministic build OpenNext Cloudflare adapter ↓ packaged Worker + assets Cloudflare deployment version ↓ custom domain routing liberating-humanity.com

Purpose served by each layer

  • Next.js: route composition, responsive UI, metadata, structured data, and reusable content components.
  • OpenNext: converts the framework output into a shape Cloudflare Workers can run instead of assuming a traditional Node server.
  • Cloudflare Worker: provides a versioned runtime close to users, routes the custom domain, and serves application responses and assets.
  • Version IDs: bind a live release to an identifiable deployment rather than a vague “latest” state.
  • Custom-domain cutover: lets the production domain move to the verified build while preserving an explicit deployment history.

Edge delivery and availability

Serving the application through Cloudflare reduces dependence on one origin location and places delivery behind Cloudflare’s global network. That supports faster content delivery and a more resilient public front door.

Why needed: mission, media, and retreat audiences are geographically distributed; the public site should not depend on a single manually managed server.

Versioned production releases

The initial preview and subsequent production updates were tied to Worker version identifiers. The custom-domain cutover and the Teachings release each retained a specific live version.

Why needed: if a regression appears, the team can identify the deployed build and compare it with the last known-good release.

DNS and email coexistence

Cloudflare also holds the public DNS layer supporting the website and authenticated sending records. Website routing, DKIM, DMARC, branding CNAMEs, and subdomain configuration must coexist without breaking one another.

Why needed: a website deployment can be correct while email authentication is broken if DNS is treated as an isolated afterthought.

Cache-aware social assets

The branded Open Graph asset is versioned so platforms with aggressive caches have a changed URL to request. A separate cache-isolated share route was prepared but remains unmerged and is not counted as delivered.

Why needed: WhatsApp and social platforms can retain stale preview images even after the page metadata has changed.

Cloudflare’s practical business value

Cloudflare created a release boundary between source code and the public domain. Instead of changing a live page directly, work could be built, tested, packaged, assigned a deployment version, verified at a temporary URL, and then served on the official domain. That makes iteration safer and makes recovery possible without reconstructing the site from memory.

Deployment model: Next.js 16 → @opennextjs/cloudflare → Cloudflare Worker + assets. Verified records include preview Worker version 78e82615-3e85-4f77-9c37-077dc0e6a6be, production cutover version 6f2d4dd5-177e-4e92-ae0c-050c0d5b4d50, and Teachings version 6b711b1e-02e6-40e0-b89d-007335978b2d.

Search, AI, and LLM discovery

The missing layer was not “more keywords.” It was a machine-readable explanation of the brand.

Traditional SEO helps a search engine index pages. AI discovery adds another requirement: assistants need a concise, authoritative account of who the organization is, what it does, which pages are official, how related entities connect, and where safety or scope boundaries apply. Without that layer, a model must infer the relationship among Paul, Liberating Humanity, Child Liberation Foundation, Santuario, retreats, teachings, and social channels from scattered page copy.

01

Canonical identity

Titles, descriptions, canonical URLs, page headings, and official entity language reduce ambiguity about which page and identity should be treated as authoritative.

02

Structured meaning

Organization, WebSite, WebPage, SearchAction, Service, and ItemList JSON-LD express page and entity relationships in machine-readable form.

03

Crawler access

robots.txt explicitly accommodates search and AI crawlers including GPTBot, OAI-SearchBot, ClaudeBot, PerplexityBot, Google-Extended, Applebot-Extended, and Meta-ExternalAgent.

04

Discovery map

sitemap.xml enumerates canonical public resources, including AI files and the Teachings library, so discovery does not rely only on internal links.

05

LLM briefing

llms.txt and llm.txt summarize mission, audiences, official pages, social profiles, retreat context, safety framing, and approved navigation.

Canonical and social metadata

Canonical tags tell crawlers which URL is primary. Route-specific titles and descriptions communicate intent. Open Graph and Twitter metadata control the title, description, and image presented when the page is shared.

Why needed: duplicate or inconsistent URLs dilute authority, while missing share metadata causes generic previews and weaker trust.

JSON-LD structured data

Schema.org objects describe the organization, website, page, services, search action, and video library as entities and relationships rather than relying only on visual copy.

Why needed: machines should not have to guess whether a name is a person, organization, service, page, or unrelated mention.

Location and topic context

The discovery layer includes Medellín and Colombia plus meditation, breathwork, trauma-informed healing, corporate wellness, Sanctuary Community, and plant-medicine education language.

Why needed: the site previously lacked enough explicit context for retreat/location and mission-adjacent discovery.

Relationship routing

The AI files explain the connection between Liberating Humanity and Santuario and direct retreat-related questions toward the official Santuario upcoming-events experience.

Why needed: assistants otherwise risk citing the wrong page or presenting the two brands as either unrelated or interchangeable.

What was implemented—and what was not claimed

Liberating Humanity’s AI files, crawler rules, sitemap entries, metadata, and structured data are live. A Search Console housekeeping process was documented, but this report does not claim verified indexing or ranking gains without Search Console readback. AI-readability improves the quality of the official source; it does not guarantee that any model will cite it.

GitHub, backups, and rollback engineering

The goal was not merely to save files. It was to preserve history, prove scope, and make recovery possible.

GitHub as the auditable source layer

Both projects use Git repositories and pull-request histories so individual changes can be reviewed, diffed, attributed, reproduced, and reversed. Liberating Humanity’s initial direct-to-main rounds were replayed through four auditable PRs after first preserving the prior final state on backup/direct-main-before-pr-replay. Santuario releases were likewise tied to scoped PRs, merge commits, tests, deployment IDs, and release proof.

A repository backup is valuable because it preserves the source and decision history needed to rebuild the application. It is stronger than a screenshot and more accountable than an unversioned folder copied from a laptop.

What the Santuario public-site backup preserved

  • Primary, Rebirth, and Detox public-site surfaces.
  • Discoverable HTML routes, images, documents, fonts, stylesheets, scripts, media, posters, and embeds.
  • Route inventories, asset/media inventories, internal/external link maps, metadata/integration maps, and source maps.
  • Raw-response evidence and hash manifests so copied artifacts can be checked for omission or corruption.
  • A locally navigable mirror and GitHub-backed record separate from the rebuilt production repository.

Backup branch before history repair

Before replaying early Liberating Humanity work through PRs, the previous direct-main final state was preserved on a dedicated backup branch. A final empty diff confirmed the replayed state matched the preserved state.

Purpose: improve auditability without losing the known-good implementation.

Release tags and prior deployments

Santuario retained rollback tag current-live-2026-10-08 and explicit prior Vercel deployment IDs in release evidence.

Purpose: rollback should name a known version, not require guessing which historic deployment was stable.

Hash manifests and raw responses

Hashes provide byte-level identity for preserved assets; raw-response evidence records what the public server actually returned at collection time.

Purpose: a folder full of similarly named files is not enough to prove completeness or integrity.

Separation of backup types

The public-site mirror was explicitly not represented as a private CMS, CRM, database, automation, submission, or account-configuration backup.

Purpose: public crawling can preserve presentation and retrievable assets, but it cannot recover private GHL records or server-side business data.

Why GitHub backups changed the risk profile

Source control created a chain from requirement → code change → review → merge → deployment → visual proof. Backups and rollback points meant corrections to testimonials, mobile layouts, Kambo presentation, boutique data, icons, or metadata did not require sacrificing the previous working state. The team could move forward while retaining evidence of what existed before.

Release engineering and quality gates

“HTTP 200” was never the finish line.

Each major release combined deterministic checks with human-visible browser verification. Automated checks catch broken contracts, links, media, metadata, and overflow; rendered screenshots catch the design failures automation often misses—dead space, tiny type, collapsed grids, weak crops, missing images, and mobile compositions that technically fit but are unusable.

Content production and operating system

A large body of media supported by a repeatable workflow.

Approximately 432 videos have been edited across the partnership, creating a substantial library for social publishing, education, campaigns, retreat storytelling, and continued audience development.

The operational system supports discovery, source-Reel capture, transcript extraction, Google Docs, client-specific Notion boards, sequential content numbering, creator and editor assignment, filmed/edit/approval/publication states, Drive assets, and read-back verification. It also distinguishes spoken content from silent, music-only, restricted, or no-speech material instead of fabricating transcripts.

That separation matters operationally: an idea is not a script; a script is not filmed media; filmed media is not an approved edit; and an approved edit is not a published post. Clear states make production volume, turnaround, bottlenecks, approvals, and final delivery measurable.

The approximate cumulative 432-video total is supplied by Alberto as an owner-provided partnership fact. It is separate from the older tracker snapshot described in the source PDF, which was incomplete and did not establish the cumulative total.
